# Atlas UI requirements — v1.4

Status: agreed scope, 2026-08-06. Four decisions taken by Damian via structured
questions; recorded in "Decisions" below with the reasoning that produced them.
This document is the build spec for a session that has not been part of the
conversation, so it names existing code and states what is already true rather
than assuming context.

Owner: Track B. Implementation is a separate build session.

## Why this exists now

The atlas has never had a front door. `symbolicworld.observer` opens directly
into a Cytoscape graph of 338 nodes with no explanation, and the published paper
describes a *frozen* release (v1.3.0, 248/669/699) that the live atlas has long
since outgrown. A reader arriving from the paper currently finds numbers that do
not match the paper and no way to reach the snapshot that does.

v1.4 adds the family layer, which is the first thing in the project that makes
the graph *queryable by meaning* rather than by node label. That capability is
invisible without UI work.

## What is true today (verified, not assumed)

- `web/src/main.js` — 236 lines, Cytoscape + fcose. Has a working **layer facet**
  (`layerBox`, values `spine` / `amplification`), volume and `claim_type` filters,
  and a **search that matches node labels only** (~10 lines, substring, fades
  non-matches). No family concept, no routing, no permalinks.
- `web/build-atlas.mjs` — 97 lines. Reads `seed.json`, writes `web/src/atlas.json`
  with `node → {id,label,type,color,cluster,x,y}` and
  `edge → {id,source,target,relation,layer,volumes,refs}`. Clusters derive
  automatically from node `type`; all six live types are mapped, so new nodes need
  no curation. Wired to `npm run sync` via `predev`/`prebuild`.
- `web/public/ledger.html` — generated by `tools/build_ledger_page.py`. Already
  ships **working client-side search across every reference record**, plus per-edge
  gate chips, RAG dots (human-validated / AI-verified / disputed) and dispute rows.
  This is the pattern to copy, not to reinvent.
- `web/public/v1.3/` — the frozen published snapshot, including its own
  `ledger.html` (29 batches, stops at b-cw12-5). **Never written to.**
- `web/public/disputes.html` + `disputes.json` — the existing precedent for
  publishing human judgements with outcomes.
- Graph at time of writing: **338 nodes / 1147 edges / 1304 references**, 47
  batches, Aion complete.

## Decisions

| # | Decision | Rationale |
|---|---|---|
| 1 | **Homepage is built around a graph-derived summary, presented as one continuous surface with the atlas** | The atlas is the product. Originally scoped as a thin gateway; revised 2026-08-06 to the R0 assembly, which demonstrates the method rather than describing it. |
| 2 | **Family definitions: progressive disclosure** — chip → side panel → full document | The step-0 test measured this directly: twelve-word hovers produced 29% confidence and "best fit" answers, while the adjudication UI showing definitions and boundary rules in full worked. Too little is worse than none. |
| 3 | **Pending edges visible and labelled** | `unclassified(pending-adjudication)` shows as a "pending review" chip and is filterable. Consistent with the dispute log and RAG dots, and preserves the reason-code distinction between "not yet judged" and "no family applies". |
| 4 | **Review queue plus attributed log** | The adjudication tool wired into the atlas, with rulings appearing in the ledger under a stable reviewer id and date — the same treatment model verdicts already get. Delivers BACKLOG's "reviewer identity as first-class provenance" early. |

## R0 — Aesthetic direction: the spectacle is the evidence

Added 2026-08-06 on Damian's brief: *"a sexy slick build that wows aesthetically,
grabs attention and then buries with the knowledge graph."* This supersedes R1's
"thin gateway" framing, which was too modest. R1's *content* requirements all stand;
R0 governs how they are presented.

**The governing rule.** Every flourish must be a claim being verified. This project's
credibility rests on the reader being able to check anything, so decoration bolted on
top of the graph would cost more than it earns. But restraint is not the same as
plainness — the material is Jung on alchemy, and its own imagery is the most striking
thing available. Use that, not a design language borrowed from somewhere else.

### R0.1 The assembly — one continuous surface, not a homepage and then an atlas

There is no "enter the atlas" button, and no page transition. The homepage *is* the
atlas at a different zoom.

1. **Near-black. One node ignites** at centre.
2. **The graph builds itself** over three to four seconds — edges drawing outward,
   nodes blooming along them, from the real `atlas.json` at its real fcose positions.
   Not a decorative particle field: 338 nodes and 1147 edges, which is the argument
   about scale made without a number.
3. **It settles and recedes**, dimming back to become ground.
4. **The hundred-word summary writes itself over the top** (R2). As each clause lands,
   the edges it rests on **light up in the graph behind it**. The reader watches a
   sentence and its evidence appear together.
5. **Scrolling lifts the prose away** and brings the graph forward. By the time the
   reader notices they are in the atlas, they are already in it.

That sequence is the whole brief in one gesture: it grabs attention, and what it grabs
attention *with* is the verification chain.

### R0.2 The palette: the Seven Metals (DECIDED, Damian, 2026-08-06)

Chosen from four candidates (`pipeline/work/atlas_palettes_v14.html`): warm
near-black ground, gold accent, cream prose — and **node type coloured by metal**,
so the legend is itself a claim about the material:

| Type | Metal | Working hex |
|---|---|---|
| Concept | Gold — Sol | `#d4af37` |
| Symbol | Silver — Luna | `#c2cdd6` |
| Figure | Copper — Venus | `#c58152` |
| Operation | Iron — Mars | `#b5502f` |
| Substance | Verdigris (the oxide) | `#63997f` |
| Motif | Lead — Saturn | `#8b96a5` |

Ground `#0b0a08`, panel `#171410`, ink `#eae3d2`, accent gold `#d4af37`. The
*system* is the decision; exact hex values are tuned at build for contrast and
colour-blind distinguishability (iron vs copper is the pair to watch). Implemented
as CSS variables plus the DOMAIN colour map in `build-atlas.mjs` — a later change
is one block in each file, so this decision is cheap to revisit and expensive only
to ignore. The rejected manuscript palette (parchment/ink/vermilion) is noted as a
candidate skin for the evidence view or print export, as a design decision, not a
user-facing toggle.

### R0.3 Typography carries the register

A display serif with letterpress weight for the summary and the section heads; the
current single `--serif` variable does everything and reads as a default. Large type,
generous measure, real line-height. The summary is a hundred words on a dark field —
it can afford to be set beautifully. **Self-hosted, no CDN** (the artifact must render
from its own files, and the v1.3 snapshot precedent is strict about it).

### R0.4 Motion with a rule

Motion only ever expresses a relationship in the data: an edge drawing = a claim being
asserted; a node brightening = it is cited by the clause you are reading; a filter
transition = the graph re-forming under a constraint. Nothing eases, floats, parallaxes
or bounces for its own sake.

`prefers-reduced-motion: reduce` skips the assembly entirely and renders the settled
graph with the summary already in place. Non-negotiable, and it must be tested, not
just declared.

### R0.5 What would cheapen it — named so it does not creep in

Glassmorphism, gradient-mesh backgrounds, floating rounded cards on a light ground,
numbers that count up on scroll, stock imagery, an AI-shimmer, and any copy in the
register of *"unlock the hidden structure of the psyche."* Every one of these says
"marketing site" and this artifact is making a claim about rigour. A reader who smells
a pitch reads the citations less carefully, which is the opposite of the point.

### R0.6 Honest scoping

This is materially more than R1 originally scoped, and it is front-end work with real
craft cost — call it the largest single item in v1.4. Three things make it tractable:
the graph, its layout and its data already exist and render; the palette is already
right; and the assembly animation is Cytoscape driving elements it already owns.

Two risks to hold: **performance** — 1147 edges animating must stay smooth on a
laptop and degrade gracefully on mobile, so the assembly is capped by time rather than
by drawing every edge if it cannot keep up; and **the first-paint window** — if the
graph takes two seconds to arrive at a black screen, the effect is a broken page, not
a reveal. Something must be on screen inside 500 ms.

## R1 — Homepage and version routing

**R1.1** A landing surface at the site root, staged per R0.1 — what this is in two
sentences, the hundred-word summary (R2), and a scroll into the atlas rather than a
button to it.

**R1.2** The method claim, stated once and plainly: *the model that proposes a
claim is never the model that signs it off.* This is the paper's central assertion
and the reason the artifact is worth trusting.

**R1.3** **Paper-reader routing, prominent and unambiguous.** The paper describes
release v1.3.0 at 248 nodes / 669 edges / 699 references. The live atlas is
larger and still growing. The homepage must say so and link to `/v1.3/`. Suggested
wording: *"The paper describes release v1.3.0 — 248 symbols, 669 relations. That
exact snapshot is preserved here. The atlas below has grown since."*

**R1.4** A version indicator visible from inside the atlas, not only on the
homepage, so a reader who lands deep still knows which graph they are looking at.

**R1.5** Live counts on the homepage read from `atlas.json` at build time, never
hardcoded. `tools/check_paper_facts.py` pins living-doc counts to head and paper
counts to the `v1.3.0` tag; the homepage is a living doc and must not drift.

## R2 — The hundred-word summary (derived, not written)

The single most persuasive artifact the project has, and it must be *generated
from the graph*, not authored.

**Origin.** The E13 narrative probe (`tools/narrative_probe.py`,
`pipeline/work/narrative_probe_result.md`) gave a model the graph with every node
label replaced by an opaque id (`N018`, `N036`…). From structure alone it produced
a coherent narrative of the opus *and correctly identified the graph as Jung's
psychological reading of alchemy*. Nothing else the project has demonstrates so
directly that the structure carries the meaning.

**R2.1** ~100 words of prose describing what the graph says, generated from the
graph.

**R2.2** **Every clause is a clickable citation.** Clicking a clause selects the
edge(s) it rests on and opens the evidence view — volume, paragraph, verbatim
quote, gate stamps. A claim a reader cannot check is exactly what this project
exists to refuse.

**R2.3** Regenerated when the graph changes materially, through the normal
proposer/gate chain — it is graph-derived content and gets the same treatment as
any other claim. It is **not** hand-edited to read better.

**R2.4** Labelled as generated, with a link to the probe method. The point is
that a machine wrote it from the structure; hiding that discards the argument.

*Scope note:* this is a bounded down-payment on the v1.8 "Story" tab, not the tab
itself. One summary, one hundred words, on one page.

## R3 — The family layer in the UI

**R3.1** Extend the existing `layerBox` facet into a family facet rather than
adding a second control beside it. `layer: amplification` is already a relation
family in disguise (57 edges over seven relation strings), so two controls would
put the same distinction on screen twice.

**R3.2** Add `relation_family` (and `relation_normalized` where present) to the
edge projection in `build-atlas.mjs`, which currently emits
`id, source, target, relation, layer, volumes, refs`.

**R3.3** Every edge shows a **family chip**. Clicking it opens a side panel with
the family's definition, its boundary note against the nearest neighbour, and two
or three seed examples — sourced from `docs/FAMILY_DEFINITIONS.md`, not
paraphrased. A "full definitions" link opens the complete document.

**R3.4** Where an edge carries a `relation_normalized`, show the **verbatim
relation as primary** and the normalized form as secondary. The verbatim string is
the verified claim; the normalized form is a layer above it. Presenting the
normalized form as the claim would misrepresent what was gated.

**R3.5** Family facet filters the graph. Combined with the existing voice filter
this yields the voice × family view that E11 exists to test.

## R4 — Pending and unclassified edges

**R4.1** Three distinct states, never conflated:
- a family chip
- `pending review` — assigned `unclassified(pending-adjudication)`, awaiting a human ruling
- `no family` — `unclassified(no-family)`, the vocabulary genuinely does not cover it

**R4.2** All three visible and filterable. ~140 edges are expected to carry
`pending review` at v1.4.

**R4.3** A one-line explanation on hover: what the state means and, for pending,
that it is queued for review. Silent absence of a chip would read as an error.

## R5 — Search that works

Current search matches node labels only. It cannot find a relation, a quote, a
paragraph, or a voice.

**R5.1** Search across: node label, relation string (verbatim and normalized),
family name, quote full text, and citation (`CW 14 §1`).

**R5.2** Typing a citation jumps to the edges citing that paragraph.

**R5.3** **Copy the working implementation in `web/public/ledger.html`** rather
than writing a new one. It already does client-side record search over every
reference at this scale.

**R5.4** Searching by family is the point at which the §8 queryability gap
visibly closes for a reader. It is the headline capability of v1.4 and should be
discoverable without instruction.

**R5.5 The works bar replaces the left-hand filter column (DECIDED, Damian,
2026-08-06).** The persistent checkbox stack is removed entirely. In its place:

- A **thin coverage strip along the bottom edge**: one segment per volume,
  width/brightness proportional to that volume's reference count, computed from
  `atlas.json` at build time. Click a segment to filter to the volume; click
  again to clear. The filter is itself a data statement — it shows where the
  graph's evidence is deep (CW 14, 9ii) and where it is thin (incidental
  volumes), which is the honesty R8.3 wants.
- **Search-token filters**: typing `CW 14` filters to the volume and renders as
  a removable chip beside the search field (extending the existing `CW 14 §1`
  citation jump). Family and layer facets move into the same chip row.
- Result: no persistent left panel at all; the graph owns the stage. The
  `claim_type` (voice) filter joins the chip row too, not a separate control.

## R6 — Citable URLs

**R6.1** A permalink per node and per edge (hash routing is sufficient).

**R6.2** Selecting a node or edge updates the URL; loading that URL restores the
selection.

**R6.3** A visible "copy link" affordance on the selection panel.

Small, and without it the artifact cannot be cited at all — which is the primary
need of the scholarly reader the paper is aimed at.

## R7 — Review queue and attributed log

**R7.1** An adjudication view inside the atlas, serving edges awaiting a human
ruling. Behaviour is already prototyped in
`pipeline/work/family_adjudication.html`: it shows the edge with qualifiers and
quote, **both model answers with their stated reasons**, the competing definitions
in full and the governing boundary rule; it requires a family and a one-line
reason; it autosaves and resumes.

**R7.2** Small stratified tranches served on request, resumable, with progress
shown — the BACKLOG "drip-fed validation" mechanism. Never a 140-item wall.

**R7.3** Each ruling records a **stable reviewer id**, a date, the ruling and the
reason.

**R7.4** Rulings appear in the ledger alongside model verdicts, the same way
dispute rows and RAG dots already do. A human ruling is evidence and belongs in
the public record with its author attached.

**R7.5** Unanchored presentation: the interface must not suggest an answer. The
E10 lesson, and the reason the model answers are shown *as competing evidence*
rather than as a default.

**R7.6** v1.4 is single-reviewer. Community submission is a v2.0 question and
needs identity, moderation and abuse handling that are out of scope here.

## R8 — The Concordance: psychology against alchemy

Added 2026-08-06 on Damian's brief: *"consider how we want to play off the core
concepts against alchemy — perhaps there is a way to show the parallels in a
clever way, make this a real didactic tool."* Mockup:
`pipeline/work/atlas_mockup_v14.html`, section III.

**The insight that makes it cheap.** Jung's thesis — alchemy is the psyche
describing itself in projected form — does not need to be *stated* by the site.
The graph already contains it as verified edges: `the-self —is-projection-of→
lapis` (CW 9ii §264), `the-unconscious —is-psychic-analogue-of→ prima-materia`
(CW 12 §431), `individuation —is-a→ coniunctio` (CW 9ii §117),
`the-self —reborn-as→ filius-regius` (CW 14 §548), and dozens more. The
Concordance is a lens on existing data, not a new dataset.

**R8.1** A two-register view: psychological concepts on one side ("The Psyche"),
alchemical carriers on the other ("The Laboratory"), bridge edges between them.
Selecting a concept surfaces its carriers; each pairing is a cited, gated edge
and clicking it opens the normal evidence view. Nothing appears in the
Concordance that is not an edge in `seed.json`.

**R8.2** The bridge set is selected by **family, not by hand**: the
symbolization / correspondence / projection families crossing from a
psychological-register node to an alchemical-register one. This makes the
Concordance the family layer's first visible payoff and keeps it maintenance-free
— new bridge edges appear as they are mined and classified.

**R8.3** A per-concept **evidence-mix strip**: what share of this concept's
references are alchemical vs other volumes. Measured today: anima 80%
alchemical, the-unconscious 78%, projection 89%; 159 of 338 nodes rest *only* on
trilogy evidence. This is didactically honest — it shows the reader where the
graph's picture of the psychology currently comes from — and it turns the CW 9i
arc into a visible experiment: as archetype theory mined without alchemical
carriers merges, the strips shift on their own.

**R8.4** **Guided pairs** for the reader who knows neither register: ~6 curated
crossings (self/lapis, opus/individuation, nigredo/unconscious, …) presented as
a short walk, each step one verified edge with its quote. Curation selects
*which* edges to walk, never edits what they say.

**R8.5** Register membership (psyche-side vs laboratory-side) is derived from
node `type` plus a small explicit list for ambiguous Concept nodes, recorded in
the build script — never inferred silently at runtime.

## Explicitly out of scope for v1.4

- The full "Story" tab (v1.8) — R2 is a bounded down-payment, not the feature.
- Community review or reader-submitted rulings (v2.0).
- Tradition-first reverse index (BACKLOG, larger).
- German cross-check UI (v1.7).

- Any RDF or nanopublication emission. Deferred by standing decision; revisited
  only if the v2.0 pilot needs machine-readable exchange.

## Design proposals — not decided, worth a view

1. **Family colour, sparingly.** Node colour already encodes `type`. Encoding
   family on edges risks two competing colour systems. Proposal: families get a
   chip and a filter, and colour only on hover-highlight of the active facet.
2. **Confidence made visible.** 1,304 references carry `high`/`medium`
   confidence and it is currently invisible. A hedged claim reading as flat is a
   small dishonesty the UI could cheaply fix.
3. **"What changed since the paper" view.** A diff between the v1.3.0 snapshot
   and head — 90 nodes, 478 edges, 605 references added. Directly serves the
   paper reader R1.3 routes, and the data for it already exists in git.
4. **The amplification layer as a worked example.** 57 edges over seven relation
   strings, with `symbolizes` appearing both inside and outside it. It is the
   clearest demonstration of why families are edge-level rather than
   string-level, and it is already in the data.
5. **Cluster labels are automatic, and Aion has shifted them.** Clusters derive
   from node `type`; the Aion arc loaded Concept and Figure heavily. Worth
   eyeballing the layout after the rebuild — likely no code, possibly a caption
   change.

## Verification

1. `npm run build` in `web/` regenerates `atlas.json` from live `seed.json`;
   counts match `seed.json` exactly.
2. `python3 tools/check_paper_facts.py` — 0 failures. Homepage counts are
   living-doc facts pinned to head; paper assertions stay pinned to `v1.3.0`.
3. `web/public/v1.3/` byte-identical before and after — checksum it.
3b. The assembly holds a smooth frame rate at 338/1147 on a laptop, something is
   painted inside 500 ms, and `prefers-reduced-motion: reduce` renders the settled
   graph with no animation at all. Tested, not asserted.
4. Every family chip resolves to a definition; no chip shows a family absent from
   `docs/FAMILY_DEFINITIONS.md`.
5. A permalink survives a round trip: copy, reload, same selection.
6. Search finds a known edge by each of: node label, relation, family, quote
   fragment, citation.
7. The hundred-word summary's clauses each resolve to at least one live edge; a
   clause whose edge has been removed must fail loudly rather than render as
   plain text.
8. Nothing is deployed. `./manage.sh deploy` is not run; publication is a
   separate, explicit decision.
